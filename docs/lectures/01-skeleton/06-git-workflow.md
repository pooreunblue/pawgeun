# 06. Git 브랜치 전략과 개발 규칙

## 1. Git의 기본 모델

- **커밋:** 어느 시점의 프로젝트 전체 스냅샷. 메시지와 부모 커밋을 가진다.
- **브랜치:** 커밋을 가리키는 이름표. 새 브랜치를 만드는 것은 이름표 하나를 더 붙이는 일이라 가볍다.
- **원격(remote):** GitHub에 있는 저장소. 내 컴퓨터의 `origin`이 가리킨다.

```
main     ●────────────────────────●          배포 가능한 상태
          \                      /
develop    ●──●──────●──────●──●            통합 브랜치
                \   /        \
feature/login    ●─●          ●─●  feature/album   기능 하나를 만드는 가지
```

```bash
git status                  # 지금 상태
git add 파일                # 커밋에 담을 것 고르기 (스테이징)
git commit -m "메시지"      # 스냅샷 저장 (내 컴퓨터에만)
git push                    # 원격에 올리기
git pull                    # 원격 변경을 가져와 합치기
git fetch                   # 가져오기만 (합치지 않음)
```

**커밋은 내 컴퓨터에만 생긴다.** `push`해야 GitHub에 올라간다. 둘을 구분하는 것이 Git 이해의 출발이다.

## 2. pawgeun의 브랜치 전략

| 브랜치 | 역할 | 직접 커밋 |
| --- | --- | --- |
| `main` | 기본 브랜치. 안정된 결과 | 금지. `develop → main` PR로만 |
| `develop` | 작업의 기준이자 통합 지점 | 금지. 기능 브랜치 PR로만 |
| `feature/{작업}` | 새 기능 | |
| `fix/{작업}` | 버그 수정 | |
| `refactor/{작업}` | 동작 변경 없는 개선 | |
| `setup/{작업}` | 저장소 공통 기초 설정 | |

브랜치 이름은 영어 소문자와 하이픈이다(`feature/member-auth`). 이름만 봐도 무슨 작업인지 알고, 슬래시 앞 접두어로 목록이 정리된다.

### 작업 시작 흐름

```bash
git checkout develop
git pull origin develop          # 최신 develop으로
git checkout -b feature/pet-album   # 거기서 새 브랜치
```

**항상 최신 `develop`에서 딴다.** 오래된 기준에서 따면 나중에 합칠 때 충돌이 크게 난다. 선행 작업의 결과물이 필요하면 그 PR이 `develop`에 합쳐진 뒤에 분기한다.

### 왜 main과 develop을 나누나

`main`을 "언제든 배포해도 되는 상태"로 지키고, 검증이 덜 된 통합 작업은 `develop`에서 받는다. 개인 프로젝트에서는 과해 보일 수 있지만, 배포를 시작하면 이 구분이 실수를 막아 준다. 처음부터 습관을 들이는 쪽을 택했다. 규모가 작아 부담이 되면 `main` 하나로 합치는 선택도 가능하다.

## 3. 커밋 규칙

```
영어카테고리 : 한글 설명
예) feat : 로그인 API 구현
```

| Type | 뜻 | 예 |
| --- | --- | --- |
| feat | 새 기능 | `feat : 회원 엔티티와 가입, 조회, 탈퇴 구현` |
| fix | 버그 수정 | `fix : 로그인 예외 처리 수정` |
| refactor | 기능 변경 없는 개선 | `refactor : 프로젝트명을 pawfect에서 pawgeun으로 변경` |
| test | 테스트 | `test : JWT 단위 테스트와 인증 API 통합 테스트 추가` |
| docs | 문서 | `docs : 회원 인증 의사결정 기록과 강의, 강의 규칙 추가` |
| chore | 설정, 기타 | `chore : Security, JWT 의존성과 설정 추가` |
| style | 포맷팅 | `style : 불필요한 import 정리` |

### 단위별 커밋

2단계(회원·인증)는 커밋 한 개가 아니라 **의미 단위로 쪼갰다.** (아래는 실제 커밋 메시지다. 이름은 두 번 바뀌어 마지막 두 줄이 이름 변경이다.)

```
chore : Security, JWT 의존성과 설정 추가
feat  : 공통 예외 처리와 생성/수정 시각 엔티티 추가
feat  : 회원 엔티티와 가입, 조회, 탈퇴 구현
feat  : JWT 발급/검증과 Security 필터 체인 구현
test  : JWT 단위 테스트와 인증 API 통합 테스트 추가
docs  : 회원 인증 의사결정 기록과 강의, 강의 규칙 추가
refactor : 프로젝트명을 pawse에서 pawfect로 변경
refactor : 프로젝트명을 pawfect에서 pawgeun으로 변경
```

이점: 리뷰어가 한 번에 한 가지만 본다. 문제가 생기면 해당 커밋만 `revert`할 수 있다. `git log`가 작업의 이야기가 된다. 기준은 "커밋 메시지를 한 문장으로 쓸 수 있는가". 쓸 수 없으면 너무 크다. 반대로 "고쳐쓰기 1", "고쳐쓰기 2" 같은 조각 커밋은 합친다.

**커밋 전에 `git status`와 `git diff --cached`(add한 내용을 보여준다)로 담길 내용을 확인한다.** `git add .`나 `git add -A`는 의도하지 않은 파일(비밀값, 빌드 산출물)을 담기 쉬워서, 담을 것을 이름으로 고르는 편이 안전하다.

## 4. Pull Request와 리뷰

PR은 "이 브랜치를 `develop`에 합쳐 달라"는 요청이다. base(합쳐질 곳)는 `develop`이다. 저장소 기본 브랜치가 `main`이라, PR을 만들 때 base를 `develop`으로 직접 바꿔야 한다. GitHub 기본값 그대로 두면 `main`에 올라가는 실수가 생긴다.

PR 본문에는 작업 내용, 의사결정 기록 경로, 테스트 체크리스트, 확인 사항을 적는다(`CLAUDE.md` 3번 템플릿). 리뷰에서 수정 요청이 오면 **새 PR을 만들지 않고 같은 브랜치에 커밋을 더 쌓는다.** PR이 자동으로 갱신된다.

```bash
git add 고친파일
git commit -m "fix : 리뷰 반영 - 예외 처리 보완"
git push
```

### 합치는 방식 (아직 정하지 않음)

| 방식 | 결과 | 특징 |
| --- | --- | --- |
| Merge commit | 브랜치 이력 + 합치는 커밋 | 이력이 그대로 남는다. 단위별 커밋 전략과 잘 맞는다 |
| Squash and merge | 커밋 하나로 합쳐짐 | `develop` 이력이 깔끔하지만 단위별 커밋이 사라진다 |
| Rebase and merge | 일렬로 이어 붙임 | 이력이 직선이지만 커밋 해시가 바뀐다 |

단위별 커밋을 남기려면 Merge commit이 적합하다. 이 선택은 첫 PR을 합칠 때 정한다.

## 5. 무엇을 커밋하지 않나: .gitignore

```
build/ , .gradle/        빌드 산출물과 캐시 (다시 만들 수 있다)
.idea/ , *.iml           IDE 개인 설정
.vscode/                 에디터 설정
(비밀값 파일)             키, 비밀번호가 든 설정
```

규칙은 **재생성 가능한 것, 개인 설정, 비밀값은 올리지 않는다**이다. 반대로 올려야 할 것: 소스, `gradlew`와 wrapper jar(01강), `compose.yaml`, 문서.

`.gitattributes`는 파일별 취급을 지정한다(줄바꿈 통일, jar는 바이너리). 한번 커밋된 파일은 `.gitignore`에 추가해도 계속 추적되므로, 실수로 올렸다면 `git rm --cached 파일`로 추적을 끊는다. 단 비밀값이 이미 올라갔다면 이력에 남으므로 **그 값을 폐기하고 새로 발급**해야 한다.

## 6. 되돌리기

| 상황 | 명령 | 안전성 |
| --- | --- | --- |
| 아직 add 안 한 수정을 버리기 | `git restore 파일` | 수정이 사라진다. 복구 불가 |
| add한 것을 되돌리기 | `git restore --staged 파일` | 안전 |
| 이미 push한 커밋 취소 | `git revert 커밋` | 안전. 취소하는 새 커밋을 만든다 |
| 머지 커밋 취소 | `git revert -m 1 커밋` | 안전. `-m 1`은 첫 번째 부모(보통 `develop` 쪽)를 기준으로 하라는 뜻. `git show 커밋`으로 부모 확인 |
| 커밋을 지우고 되돌아가기 | `git reset --hard 커밋` | **위험.** 작업이 사라진다. push한 이력에는 쓰지 않는다 |

공유된(push된) 이력은 고쳐 쓰지 않고 `revert`로 덮는다. 다른 사람이 그 이력 위에서 작업했을 수 있어서다.

## 7. 충돌

같은 파일의 같은 부분을 두 브랜치가 바꾸면 합칠 때 충돌한다.

```
<<<<<<< HEAD
내 쪽 내용
=======
상대 쪽 내용
>>>>>>> develop
```

두 내용을 보고 의도한 최종 모양으로 직접 고치고 마커를 지운 뒤 `add` → `commit`한다. 충돌을 줄이는 습관: 브랜치를 짧게 유지하고, 작업 도중 `git fetch` 후 `git merge origin/develop`(fetch는 `origin/develop`만 갱신한다)으로 가끔 합쳐서 차이가 커지지 않게 한다.

## 8. 기록을 남기는 습관

- 커밋 메시지: 무엇을 했나
- PR 본문: 왜, 어떻게 확인했나
- `docs/decisions/`: 왜 이 방법을 골랐나, 다른 대안은 무엇이었나 (`CLAUDE.md` 4번)
- `docs/lectures/`: 이 개념은 무엇인가

네 곳의 질문이 다르다. 코드만으로는 "왜"가 남지 않는다. 몇 달 뒤의 내가 "왜 이렇게 했지?"에 답하려면 기록이 필요하다.

## 9. CLAUDE.md는 무엇인가

Claude Code가 이 프로젝트에서 일할 때 따라야 할 규칙 문서다. 사람에게는 협업 규칙(브랜치, 커밋, PR) 문서이기도 하다. 작업 시작 전 모델/Effort 제안 → 동의 → "시작하자" → 개발 → (지시 시) 커밋 → 의사결정 기록 → (지시 시) PR의 흐름을 정의한다. 커밋과 PR은 "시작하자"만으로 자동 진행하지 않고, 별도로 지시할 때만 실행한다. 규칙을 문서로 두면 사람이 바뀌어도 같은 방식으로 일하게 된다.

## 직접 해 보기

1. `git log --oneline --graph --all`로 지금까지의 브랜치와 커밋 흐름을 보자. `feature/member-auth`와 `develop`이 어디서 갈라졌는가?
2. 연습용 브랜치 `feature/practice`를 만들어 파일 하나를 고치고 두 번에 나누어 커밋해 보자. 메시지가 규칙을 따르는가? 끝나면 `git checkout develop`으로 먼저 이동한 뒤(지금 있는 브랜치는 지울 수 없다) `git branch -D feature/practice`로 지운다.
3. `git diff origin/develop..origin/feature/member-auth --stat`으로 두 브랜치의 차이를 파일 단위로 보자. (새로 clone했다면 로컬 브랜치가 없으니 `origin/`을 붙인 이름을 쓴다)
4. 일부러 `.gitignore`에 `docs/`를 넣었다가 `git status`가 어떻게 변하는지 보고 원복해 보자.
