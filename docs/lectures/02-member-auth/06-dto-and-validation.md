# 06. DTO, record, Bean Validation

> 이 강의 한 줄 요약: **DTO는 창구에서 주고받는 "신청서 양식"이고, Bean Validation은 그 양식을 접수 직원이 훑어보는 "기재 요령 체크리스트"다.**

## 1. DTO란

DTO(Data Transfer Object)는 **요청과 응답의 모양**만 정의한 객체다. 엔티티와 따로 만든다.

### 비유: 병원의 진료 기록 원본과 진단서

병원에는 환자의 **진료 기록 원본**(엔티티)이 있다. 거기엔 병력, 처방, 내부 메모까지 전부 들어 있다. 환자가 회사에 낼 서류를 달라고 하면, 원본을 통째로 복사해 주지 않는다. 필요한 내용만 담은 **진단서**(응답 DTO)를 따로 발급한다.

환자가 접수할 때도 원본 기록지에 직접 쓰게 하지 않는다. **접수 신청서**(요청 DTO)를 따로 주고, 직원이 확인한 뒤 원본에 옮겨 적는다.

```text
요청 JSON ──▶ SignUpRequest (접수 신청서) ──▶ 서비스 ──▶ Member (원본 기록) ──▶ DB
응답 JSON ◀── MemberResponse (진단서)    ◀── 서비스 ◀── Member (원본 기록)
```

### 엔티티를 그대로 내보내면 안 되는 이유

1. **정보 누출.** `Member`를 그대로 JSON으로 만들면 `passwordHash`가 응답에 실린다. 진료 기록 원본을 통째로 복사해 준 셈이다. `MemberResponse`는 `id, email, nickname`만 가져서, 이 사고가 **구조적으로 불가능**하다. "조심해서 빼자"가 아니라 "애초에 칸이 없다"는 것이 핵심이다.
2. **API와 DB가 묶인다.** 엔티티를 그대로 내보내면 컬럼 이름 하나만 바꿔도 JSON 필드 이름이 바뀌어 앱이 깨진다. 병원 내부 양식을 개편했더니 회사들이 받는 진단서 양식까지 바뀌는 꼴이다. DTO를 두면 DB를 바꿔도 API는 그대로 둘 수 있다.
3. **요청에서도 위험하다(과다 바인딩, mass assignment).** 요청을 엔티티로 받으면 클라이언트가 `id`나 권한 같은 필드를 임의로 채워 보낼 수 있다. 환자가 접수 신청서 대신 원본 기록지를 받아서 "담당의 소견: 완치" 칸을 스스로 채워 넣는 상황이다. 요청 DTO에는 사용자가 채워도 되는 칸만 있다.

## 2. record: DTO에 딱 맞는 문법

```java
// 이 한 줄이 필드 3개, 생성자, getter, equals/hashCode/toString을 모두 만든다
public record SignUpRequest(String email, String password, String nickname) { }
```

`record`(자바 16+)는 **불변 데이터 묶음**이다. 필드, 생성자, getter(`email()`처럼 `get` 없이), `equals/hashCode/toString`을 자동 생성한다. Lombok 없이 한 줄이다. Jackson이 JSON을 record로 바로 변환한다.

### 비유: 인쇄된 영수증

record는 **인쇄된 영수증**이다. 한번 출력되면 내용을 고칠 수 없다(setter 없음, 필드가 `final`). 신청서가 서비스를 거치는 동안 누가 중간에 내용을 바꿔 버릴 걱정이 없다. 데이터를 "전달"만 하는 DTO에 딱 맞는 성질이다.

Django의 serializer/form과 비슷한 자리지만, 모양 정의와 검증 규칙이 어노테이션으로 **한곳에** 모인다.

## 3. Bean Validation: 어노테이션으로 검증

### 비유: 신청서 각 칸 옆의 "기재 요령"

관공서 신청서를 보면 칸마다 작은 글씨로 "필수", "숫자만", "20자 이내" 같은 기재 요령이 있다. 접수 직원은 이 요령대로 훑어보고, 틀리면 **담당 부서로 넘기기 전에** 돌려준다.

```java
public record SignUpRequest(
    @NotBlank @Email @Size(max = 100) String email,                  // 필수, 이메일 모양, 100자 이내
    @NotBlank @Pattern(regexp = "...", message = "...") String password,  // 필수, 비밀번호 규칙
    @NotBlank @Size(min = 2, max = 30) String nickname) { }          // 필수, 2~30자
```

컨트롤러에서 `@Valid`를 붙이면 검증이 실행된다. `@Valid`는 "접수 직원님, 이 신청서 기재 요령대로 확인해 주세요"라는 표시다. 이게 없으면 어노테이션을 달아 놔도 아무도 확인하지 않는다.

```java
// @Valid: 요청 본문을 SignUpRequest로 바꾼 뒤, 붙어 있는 규칙대로 검사한다
public MemberResponse signUp(@Valid @RequestBody SignUpRequest request)
```

검증에 실패하면 컨트롤러 메서드가 **실행되기 전에** `MethodArgumentNotValidException`이 던져지고, `GlobalExceptionHandler`가 400 JSON으로 바꾼다(07강). 담당 부서(서비스)는 잘못 쓴 신청서를 아예 보지 않는다.

### 자주 쓰는 어노테이션과 함정

| 어노테이션 | 검사 | 주의 |
| --- | --- | --- |
| `@NotNull` | null 아님 | 빈 문자열 `""`은 통과 |
| `@NotEmpty` | null/빈 문자열 아님 | 공백 `" "`은 통과 |
| `@NotBlank` | null/빈 문자열/공백만 아님 | 문자열은 대부분 이걸 쓴다 |
| `@Size(min, max)` | 길이 | null은 통과(그래서 `@NotBlank`와 함께) |
| `@Email` | 이메일 형식 | 느슨한 검사. 실제 존재 확인은 아니다 |
| `@Pattern` | 정규식 | null은 통과 |

세 개의 "Not" 시리즈를 칸 비유로 정리하면 이렇다.

```text
@NotNull  : 칸이 "있기만" 하면 통과        → 빈칸("")도 통과
@NotEmpty : 칸에 "뭔가" 적혀 있으면 통과   → 스페이스만 친 것(" ")도 통과
@NotBlank : 칸에 "진짜 글자"가 있어야 통과 → 가장 엄격
```

`@Size`, `@Pattern`이 null을 통과시키는 것은 의도된 설계다. "값이 있다면 이 모양이어야 한다"는 뜻이고, "값이 꼭 있어야 한다"는 `@NotBlank`/`@NotNull`의 몫이다. 각자 한 가지 일만 한다. 그래서 둘을 함께 쓴다.

### 비밀번호 정규식 해부

```text
^(?=.*[A-Za-z])(?=.*\d)[\x21-\x7E]{8,64}$
 │  └ 영문이 하나 이상 있어야 함 (전방탐색)
 │              └ 숫자가 하나 이상 있어야 함
 │                         └ ASCII 출력 가능 문자(공백 제외)로 8~64자
 └ 문자열 처음부터 끝까지 검사
```

**전방탐색 `(?=...)`**은 "앞을 슬쩍 훑어보기만 하고 위치는 안 옮긴다"는 뜻이다. 검사관이 서류를 쭉 훑어보며 "영문 있음 ✓", 다시 처음부터 "숫자 있음 ✓"을 체크한 뒤, 마지막으로 전체 길이와 문자 종류를 확인하는 식이다. 조건 여러 개를 순서 상관없이 동시에 걸 때 쓴다.

글자 수 상한을 64로 둔 것은 BCrypt의 72바이트 한계(03강) 때문이다. 바이트와 글자 수가 같아지도록 ASCII로 제한했다.

## 4. 검증은 어디서 하나

### 비유: 접수 창구 vs 담당 부서

| 층 | 검증 | 예 | 비유 |
| --- | --- | --- | --- |
| DTO (`@Valid`) | **형식**: 비어 있나, 길이, 모양 | 이메일 형식, 비밀번호 규칙 | 접수 창구: 서류만 보고 판단 |
| 서비스 | **업무 규칙**: DB를 봐야 아는 것 | 이메일 중복 | 담당 부서: 기록을 조회해야 판단 |

접수 직원은 "생년월일 칸에 글자를 썼네요"는 바로 알지만, "이 분은 이미 등록된 분이네요"는 기록실을 조회해야 안다. 중복 이메일은 DTO 어노테이션으로 검사할 수 없다(DB 조회 필요). 서비스에서 `BusinessException`으로 처리한다. 두 층을 섞지 않는다.

### 프런트 검증이 있어도 서버 검증은 필수

Flutter 앱에서 입력값을 검사해도, **서버 검증은 반드시 필요하다.** 앱을 거치지 않고 `curl`이나 Postman으로 API를 직접 호출할 수 있기 때문이다.

비유: 앱의 검증은 **집에서 서류를 미리 확인해 주는 친절한 안내문**이다. 그걸 안 읽고 엉터리로 써 오는 사람도 있다. 창구는 언제나 다시 확인한다. **서버는 클라이언트를 믿지 않는다.**

## 5. 변환 위치

엔티티 → DTO 변환은 `MemberResponse.from(member)` 정적 팩토리로 DTO 안에 두었다.

```java
// 원본 기록(Member)에서 진단서(MemberResponse)에 필요한 칸만 옮겨 적는다
MemberResponse.from(member);
```

"진단서 양식이 스스로 원본에서 필요한 칸을 골라 온다"는 구조다. 규모가 커지면 매퍼 클래스로 뺄 수 있지만 지금은 한 줄이라 과하다.
