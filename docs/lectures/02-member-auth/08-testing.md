# 08. 테스트: 단위 테스트와 통합 테스트

> 이 강의 한 줄 요약: **단위 테스트는 "부품 하나를 작업대에서 검사"하는 것이고, 통합 테스트는 "완성된 차를 실제로 몰아 보는" 것이다. 둘 다 필요하지만 하는 일이 다르다.**

## 1. 두 종류를 나눠 쓴다

### 비유: 자동차 공장의 품질 검사

- **단위 테스트 = 부품 검사.** 브레이크 패드 하나를 작업대에 올려놓고 마찰력을 잰다. 차 전체를 조립할 필요가 없어 빠르다. 패드 자체의 결함을 정밀하게 잡는다.
- **통합 테스트 = 시운전.** 다 조립한 차를 트랙에서 몰아 본다. 시간이 오래 걸린다. 하지만 "패드는 멀쩡한데 브레이크 선을 반대로 연결했다" 같은 **조립 실수**는 시운전에서만 잡힌다.

| | 단위 테스트 (부품 검사) | 통합 테스트 (시운전) |
| --- | --- | --- |
| 대상 | 클래스 하나 | 여러 계층을 실제로 연결 |
| 스프링 | 안 띄움 | 띄움 |
| 속도 | 밀리초 | 수 초 |
| 이 프로젝트 | `JwtProviderTest` | `AuthApiTest` |
| 잡아내는 것 | 로직 오류 | 설정·연결 오류 (필터 순서, 빈 등록, SQL) |

규칙은 이렇다. **로직이 복잡한 곳은 단위 테스트로 촘촘히, 큰 흐름은 통합 테스트로 몇 개만.** 부품 하나 확인하려고 매번 차 전체를 조립해 몰면 공장이 멈춘다. 전부 통합 테스트로 쓰면 느려져서 아무도 안 돌린다. 안 돌리는 테스트는 없는 것과 같다.

## 2. 단위 테스트: JwtProviderTest

### 생성자 주입이 테스트를 쉽게 만든다

`JwtProvider`는 스프링 없이 `new`로 만들 수 있다. 의존하는 것이 `JwtProperties` 값 하나뿐이어서다.

```java
// 스프링 없이 부품만 꺼내 작업대에 올린다
JwtProvider provider = new JwtProvider(new JwtProperties(SECRET, ...));
```

이것이 **생성자 주입**의 이점이다. 필요한 부품을 생성자로 건네주게 되어 있으니, 테스트에서도 직접 건네주면 된다. 필드 주입(`@Autowired private ...`)이었다면, 스프링이라는 **조립 라인**을 돌려야만 부품이 끼워진다. 작업대에서 단독으로 검사하기 어렵다.

### 테스트 이름은 한글 문장으로

테스트 이름을 한글 문장으로 써서 **무엇을 보장하는지**가 이름에 드러나게 했다. 테스트가 실패하면 보고서에 이름이 뜬다. "test3 실패"보다 "만료된_토큰은_거부한다 실패"가 훨씬 빨리 원인을 알려 준다.

```java
@Test
void 만료된_토큰은_거부한다() {
    // 준비: 만료 시각이 이미 지난 토큰을 직접 만든다 (30분을 기다리지 않는다)
    String expired = Jwts.builder()....expiration(과거 시각)....compact();

    // 실행 + 검증: 파싱하면 INVALID_TOKEN을 담은 BusinessException이 나야 한다
    assertThatThrownBy(() -> provider.parseMemberId(expired))
        .isInstanceOfSatisfying(BusinessException.class,
            e -> assertThat(e.getErrorCode()).isEqualTo(ErrorCode.INVALID_TOKEN));
}
```

### 시간을 기다리지 않는다

30분을 기다릴 수 없으니 만료 시각이 **이미 지난** 토큰을 직접 만들어 넣었다.

비유: 우유가 상했을 때 경고가 뜨는지 확인하려고 2주를 기다리지 않는다. **유통기한이 지난 라벨을 붙인 우유**를 만들어 냉장고에 넣어 보면 된다. 테스트하기 어려운 상황은 입력을 직접 만들어 주면 된다.

### 실패 경로가 중심이다

여섯 개 테스트가 다루는 것: 정상 왕복, 만료, 다른 키, 내용 변조, 쓰레기 문자열, 약한 키. 정상은 하나, 나머지 다섯은 모두 **실패해야 하는** 경우다.

비유: 현관 자물쇠를 검사할 때 "맞는 열쇠로 열린다"만 확인하면 절반이다. "틀린 열쇠로는 **안** 열린다", "철사로 쑤셔도 **안** 열린다"를 확인해야 자물쇠로서 의미가 있다. **정상 경로보다 실패 경로**가 보안 테스트의 중심이다.

## 3. 통합 테스트: AuthApiTest

```java
@SpringBootTest        // 애플리케이션 전체를 띄움 (차를 다 조립)
@AutoConfigureMockMvc  // 가짜 HTTP 클라이언트(MockMvc) 준비 (트랙 위의 테스트 드라이버)
class AuthApiTest { ... }
```

### MockMvc: 실내 주행 시험장

`MockMvc`는 실제 네트워크 없이 서블릿 환경에 요청을 던진다. 진짜 도로(네트워크) 대신 **실내 시험장**에서 차를 모는 셈이다. 포트를 열지 않아 빠르고 안정적이지만, 차(애플리케이션)는 진짜다.

중요한 점: **Security 필터 체인을 포함해** 통과한다. 그래서 401/403, 토큰 필터까지 검증된다. 04강에서 본 "필터 순서", "permitAll 경로" 같은 조립 실수는 여기서만 잡힌다.

```java
// 토큰을 붙여 /me를 호출하면
mockMvc.perform(get("/api/members/me").header("Authorization", "Bearer " + token))
    .andExpect(status().isOk())                               // 200이어야 하고
    .andExpect(jsonPath("$.email").value("a@example.com"));   // 응답의 email이 가입한 값이어야 한다
```

- **`jsonPath("$.email")`:** 응답 JSON에서 `email` 값을 꺼내 비교한다. `$`는 JSON 전체(루트)를 뜻한다.
- **`.doesNotExist()`:** 있으면 **안 되는** 필드(비밀번호)를 확인한다. "빠져야 할 것"도 테스트한다. 06강의 "응답에 해시가 실리면 안 된다"를 코드로 지키는 장치다.
- **`@BeforeEach`에서 `memberRepository.deleteAll()`:** 매 테스트를 **깨끗한 상태**에서 시작한다. 시운전마다 차를 원래 상태로 되돌리는 것이다. 앞 테스트에서 가입한 회원이 남아 있으면, 다음 테스트의 "가입 성공"이 "중복 가입"으로 실패할 수 있다. 테스트끼리 서로 영향을 주지 않아야 하고, 실행 순서에 의존하면 안 된다.

### 테스트용 DB

`src/test/resources/application.properties`가 운영 설정을 덮어쓴다.

```properties
# 인메모리 H2를 PostgreSQL 호환 모드로 사용
spring.datasource.url=jdbc:h2:mem:pawgeun;MODE=PostgreSQL
# 테스트에서는 Docker를 띄우지 않음
spring.docker.compose.enabled=false
# 테스트 전용 키 (운영 키와 무관)
pawgeun.jwt.secret=test-...
```

비유: 진짜 PostgreSQL 대신 쓰는 H2는 **연습용 모형 도로**다.

- 장점: 빠르고 Docker가 필요 없다. 메모리에만 있어서 테스트가 끝나면 흔적도 없다.
- 단점: 모형 도로는 진짜 도로가 아니다. H2는 PostgreSQL을 **흉내** 낼 뿐이다. 운영 DB 고유 기능(JSON 컬럼, 특정 쿼리)을 쓰기 시작하면 모형 도로에서 통과한 차가 진짜 도로에서 멈출 수 있다. 그때는 Testcontainers로 **진짜 PostgreSQL**을 띄우는 쪽으로 옮긴다. 결정 근거는 `docs/decisions/member-auth.md`에 있다.

## 4. 좋은 테스트의 기준

| 기준 | 설명 | 비유 |
| --- | --- | --- |
| 하나의 이유로만 실패한다 | 한 테스트는 한 가지를 확인한다 | 경고등 하나는 문제 하나를 가리킨다. "엔진 이상" 등이 브레이크 문제로도 켜지면 쓸모없다 |
| 이름이 명세다 | 실패했을 때 이름만 보고 무엇이 깨졌는지 안다 | 계기판 경고등 옆의 그림 |
| 독립적이다 | 순서, 외부 상태에 의존하지 않는다 | 시운전마다 차를 초기화 |
| 실패 경로를 포함한다 | 성공만 있는 테스트는 절반이다 | 틀린 열쇠로 안 열리는지도 확인 |
| 구현이 아니라 동작을 검증한다 | 내부 메서드 호출 여부보다 응답과 DB 결과를 본다 | 엔진 내부 배선이 아니라 "밟으면 서는가"를 본다 |

마지막 기준이 특히 중요하다. 내부 구현을 검증하는 테스트는, 기능은 그대로인데 코드를 정리(리팩터링)만 해도 깨진다. 그러면 테스트가 "고치지 마" 하는 족쇄가 된다. **결과**를 보는 테스트는 내부를 마음껏 고쳐도 계속 통과한다.

## 5. 이번 단계에서 테스트가 잡아 준 것

`AuthApiTest.탈퇴하면...`은 "탈퇴한 회원의 토큰으로 `/me`를 호출하면 404"를 고정한다.

02강에서 "토큰 서명은 유효해도 회원은 이미 없을 수 있다"는 약점을 봤다. 출입증은 진짜인데 사원 명부엔 이름이 없는 상황이다. 이 테스트는 그 약점이 **어떻게 처리되는지**를 코드로 못 박는다. 누군가 나중에 "매번 DB 조회하는 거 느리니까 빼자"고 고치면 이 테스트가 바로 빨간불을 켠다.
