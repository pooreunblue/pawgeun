# 03. 비밀번호는 어떻게 저장하나: 해시와 BCrypt

> 이 강의 한 줄 요약: **비밀번호는 "갈아 버린 고기"로 저장한다. 고기를 다시 원래 덩어리로 되돌릴 순 없지만, 같은 고기를 같은 방식으로 갈면 같은지 비교할 수는 있다.**

## 1. 평문 저장은 왜 안 되나

### 비유: 아파트 관리실의 열쇠 보관함

관리실이 모든 세대의 **진짜 열쇠**를 보관함에 걸어 둔다고 하자. 보관함 하나만 털리면 아파트 전체가 뚫린다. 게다가 사람들은 집 열쇠, 차 열쇠, 사무실 열쇠를 같은 모양으로 맞춰 두는 경우가 많다(같은 비밀번호 재사용). 그러면 피해가 아파트 밖까지 번진다.

DB 유출은 생각보다 흔하다. 백업 파일 분실, SQL 인젝션, 개발자 실수, 내부자. 평문으로 저장했다면 그 순간 모든 회원의 비밀번호가 그대로 노출된다.

중요한 사실: **서비스 운영자조차 원래 비밀번호를 알 필요가 없다.** 로그인 때 "맞는지"만 확인하면 된다. 관리실은 열쇠를 보관할 필요 없이, 문 앞에서 "이 열쇠가 맞는 열쇠인가"만 알면 된다.

## 2. 암호화가 아니라 해시

### 비유: 금고 vs 믹서기

- **암호화 = 금고.** 물건을 넣고 잠근다. 열쇠가 있으면 원래 물건을 **그대로 꺼낼 수 있다.**
- **해시 = 믹서기.** 딸기를 넣고 갈면 딸기 주스가 된다. 주스를 다시 딸기로 **되돌릴 방법은 없다.** 하지만 같은 딸기를 같은 믹서기에 갈면 **항상 같은 주스**가 나온다.

| | 암호화 (금고) | 해시 (믹서기) |
| --- | --- | --- |
| 방향 | 양방향 (키가 있으면 복호화) | 단방향 (원문 복원 불가) |
| 용도 | 나중에 원문이 필요할 때 (예: 주소, 전화번호) | 같은지만 확인할 때 |

비밀번호는 원문이 필요 없으니 해시한다. 로그인 때는 입력값을 같은 방식으로 갈아서, 저장된 주스와 같은지 비교한다.

암호화로 저장하면 안 되는 이유: 금고 열쇠(복호화 키)도 결국 서버 어딘가에 있다. DB와 함께 키가 털리면 전부 풀린다. 해시는 애초에 되돌리는 열쇠가 존재하지 않는다.

## 3. 그냥 SHA-256이면 안 되나

SHA-256도 해시다. 그런데 비밀번호용으로는 안 된다. 두 가지 이유가 있다.

### 이유 1. 너무 빠르다

SHA-256은 원래 대용량 파일이 변조됐는지 빨리 확인하려고 만든 것이라 **빠를수록 좋은** 해시다. 그래픽카드 하나가 초당 수십억 번 계산한다.

공격자가 유출된 해시를 손에 넣으면, 흔한 비밀번호 수억 개를 하나씩 갈아서 같은 주스가 나오는지 맞춰 본다(무차별 대입). 빠른 믹서기는 공격자에게도 빠르다.

비유하자면 **자물쇠 하나를 따는 데 0.000001초**가 걸리는 셈이다. 비밀번호 해시는 일부러 **느려야** 한다.

### 이유 2. 같은 입력은 같은 해시

`password1`을 갈면 누가 갈든 항상 같은 주스가 나온다. 그러면 공격자는 **미리** 흔한 비밀번호 수억 개를 갈아서 "주스 → 원래 과일" 대조표를 만들어 둔다(레인보우 테이블). 유출된 해시를 표에서 찾기만 하면 된다.

또, 같은 비밀번호를 쓴 회원들은 해시도 같다. DB를 보면 "이 100명은 비밀번호가 같네"가 드러나고, 한 명만 알아내면 100명이 동시에 뚫린다.

## 4. 해법: 솔트 + 느린 해시

### 솔트(salt): 사람마다 다른 비밀 재료

솔트는 이름 그대로 **소금**이다. 같은 딸기라도 사람마다 다른 무작위 재료를 한 숟갈씩 넣고 갈면, 주스 맛이 전부 달라진다.

- 철수의 `password1` + 솔트 `x7Q...` → 주스 A
- 영희의 `password1` + 솔트 `k2M...` → 주스 B (A와 완전히 다름)

효과:

- 같은 비밀번호여도 해시가 달라진다. "100명이 같은 비밀번호"가 드러나지 않는다.
- 미리 만든 대조표가 **무용지물**이 된다. 공격자는 회원 한 명 한 명마다 솔트를 넣어 다시 갈아야 한다.

솔트는 비밀이 아니다. 해시 옆에 같이 저장해도 된다. 솔트의 목적은 "숨기기"가 아니라 "사람마다 다르게 만들기"다.

### 작업 비용(cost): 일부러 오래 돌리는 믹서기

해시 계산을 일부러 수천 번 반복해서 느리게 만든다. 로그인하는 회원은 한 번만 계산하니 0.1초 정도 느려져도 모른다. 하지만 2억 번 대입하려는 공격자에게는 0.1초 × 2억 = 2천만 초, 한 줄로 차례차례 계산하면 **약 231일**이 걸린다.

물론 공격자는 컴퓨터(GPU) 여러 대로 **동시에** 돌릴 수 있어서, 100대면 이틀 남짓으로 줄어든다. 그래서 느린 해시는 "절대 못 뚫는 벽"이 아니라 **공격 비용을 수만~수십만 배 비싸게 만드는 장치**로 이해해야 한다. SHA-256처럼 빠른 해시였다면 같은 작업이 몇 초면 끝난다.

하드웨어가 빨라지면 cost를 올린다. 자물쇠를 시대에 맞게 더 튼튼하게 바꾸는 것이다.

BCrypt는 솔트와 cost를 **기본으로** 제공한다. 개발자가 따로 신경 쓸 필요가 없다.

## 5. BCrypt 결과물 해부

```text
$2a$10$N9qo8uLOickgx2ZMRZoMye IjZAgcfl7p92ldGxad68LJZdL17lhWy
│ │  │  └──── salt (22자) ────┘ └────────── 해시 (31자) ──────────┘
│ │  └ cost = 10  (2^10 = 1024번 반복)
│ └ 버전
└ 구분자
```

솔트와 cost가 결과 문자열 **안에 같이** 들어 있다. 마치 주스 병 라벨에 "소금 종류: x7Q, 갈은 횟수: 1024번"이 적혀 있는 것과 같다. 그래서

- DB 컬럼은 하나(`passwordHash`)면 된다.
- 비교할 때 `matches(평문, 저장된해시)`가 라벨을 읽어 같은 솔트·같은 cost로 다시 갈아서 비교한다.

```java
passwordEncoder.encode("password1");              // 호출할 때마다 결과가 다르다 (솔트가 매번 새로 뽑혀서)
passwordEncoder.matches("password1", 저장된해시);   // true: 라벨의 솔트를 꺼내 같은 방식으로 비교
```

그래서 **`equals`로 해시를 비교하면 안 된다.** `encode`를 다시 호출하면 새 솔트가 들어가 다른 값이 나오기 때문이다. 항상 `matches`를 쓴다.

## 6. 이 프로젝트 코드에서

```java
// 가입: MemberService.signUp
// 평문을 BCrypt로 갈아서 저장한다. 평문은 어디에도 남지 않는다.
.passwordHash(passwordEncoder.encode(rawPassword))

// 로그인: AuthService.login
// 입력값과 저장된 해시를 matches로 비교한다.
if (!passwordEncoder.matches(request.password(), member.getPasswordHash())) { ... }
```

`PasswordEncoder`는 인터페이스이고 `SecurityConfig`가 `BCryptPasswordEncoder` 빈을 등록한다. 서비스는 구현체를 모른다.

비유: 서비스는 "믹서기"라는 **콘센트 규격**만 안다. 꽂혀 있는 게 A사 믹서기인지 B사 믹서기인지 모른다. 나중에 알고리즘을 Argon2 같은 것으로 바꿔도 서비스 코드는 그대로다.

단, **서비스 코드가 그대로라는 것이지 기존 데이터가 그대로 통한다는 뜻은 아니다.** 이미 DB에 저장된 해시는 BCrypt 믹서기로 간 결과물이다. 믹서기를 Argon2로 통째로 바꾸면 기존 회원의 비밀번호를 검증할 수 없다(아래 함정 4).

## 7. 알아둘 함정

### 함정 1. BCrypt는 72바이트까지만 읽는다

믹서기 투입구가 72바이트 크기라, 그 뒤에 넣은 재료는 무시된다(구현에 따라 예외). 즉 73번째 글자부터 다르게 써도 같은 비밀번호로 취급될 수 있다.

한글은 UTF-8에서 글자당 3바이트라 24자만 넘어도 한계에 닿는다. 그래서 `SignUpRequest`가 비밀번호를 ASCII 출력 가능 문자(`\x21-\x7E`)로 제한해 **글자 수 = 바이트 수**가 되게 했다. 최대 64자라 72바이트 안에 확실히 들어온다(06강).

### 함정 2. 로그인 실패 메시지를 통일한다

"없는 이메일입니다"와 "비밀번호가 틀렸습니다"를 다르게 알려주면, 공격자가 이메일 목록을 하나씩 넣어 보며 **누가 가입했는지** 알아낼 수 있다(사용자 열거). 그래서 `AuthService`는 두 경우 모두 `LOGIN_FAILED`를 던진다.

그런데 말을 통일해도 **응답 시간**이 다르면 들킨다(타이밍 공격).

- 없는 이메일: DB 조회 후 바로 실패 → 빠름 (예: 5ms)
- 있는 이메일 + 틀린 비밀번호: DB 조회 + BCrypt 계산 → 느림 (예: 80ms)

비유: 문을 두드렸을 때 "없어요"라는 대답이 **즉시** 오면 빈집이고, **한참 뒤에** 오면 누가 안에서 확인하고 대답한 것이다. 대답 내용이 같아도 걸린 시간으로 알 수 있다.

그래서 이메일이 없을 때도 미리 만들어 둔 **더미 해시**와 `matches`를 돌려 같은 비용을 치른다. 빈집이어도 일부러 한참 기다렸다가 대답하는 것이다.

로그인 횟수 제한(무차별 대입 방어)은 아직 없다.

### 함정 3. 비밀번호를 로그에 남기지 않는다

요청 로깅을 켤 때 `password` 필드를 가려야 한다. 해시를 아무리 잘 해도 로그 파일에 평문이 찍히면 소용없다. 응답 DTO에 해시도 넣지 않는다(06강).

### 함정 4. 인코더를 바꾸면 기존 해시가 검증되지 않는다

`PasswordEncoder` 빈을 `BCryptPasswordEncoder`에서 `Argon2PasswordEncoder`로 그냥 바꾸면, `Argon2PasswordEncoder`는 `$2a$...`로 시작하는 BCrypt 해시를 읽지 못한다. **기존 회원 전원이 로그인에 실패한다.**

| 방법 | 동작 | 장단점 |
| --- | --- | --- |
| 인코더만 교체 | 새 알고리즘으로만 검증 | 가장 단순하지만 기존 해시가 전부 무효. 신규 서비스에서만 가능 |
| `DelegatingPasswordEncoder` + 알고리즘 식별자 | 해시 앞에 `{bcrypt}`, `{argon2}` 같은 꼬리표를 붙이고, 꼬리표를 보고 맞는 인코더로 검증 | 여러 알고리즘이 공존. 저장된 기존 해시에는 꼬리표가 없으므로 마이그레이션이 필요 |
| `DelegatingPasswordEncoder` + 기본 검증을 BCrypt로 지정 | 꼬리표 없는 해시는 BCrypt로 검증(`setDefaultPasswordEncoderForMatches`) | 기존 데이터를 건드리지 않고 전환 가능. 로그인 성공 시 새 알고리즘으로 다시 해시해 저장하면 점진적으로 옮겨 간다 |

비유: 믹서기를 바꿀 때는 옛 믹서기를 바로 버리지 않는다. 그릇마다 "어느 믹서기로 갈았는지" 꼬리표를 붙이거나, 꼬리표 없는 그릇은 옛 믹서기로 확인하기로 정해 두고 둘 다 놔둔다.

현재 이 프로젝트는 `BCryptPasswordEncoder`를 직접 쓴다. 알고리즘을 바꿀 일이 생기면 그때 위 방법 중 하나를 골라야 한다.
