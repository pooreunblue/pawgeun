# 03. 비밀번호는 어떻게 저장하나: 해시와 BCrypt

## 1. 평문 저장은 왜 안 되나

DB가 유출되면(백업 파일 분실, SQL 인젝션, 개발자 실수) 모든 회원의 비밀번호가 그대로 노출된다. 사람들은 여러 사이트에 같은 비밀번호를 쓰므로 피해가 다른 서비스로 번진다. 서비스 운영자조차 원래 비밀번호를 알 필요가 없다. 로그인 때 "맞는지"만 확인하면 된다.

## 2. 암호화가 아니라 해시

| | 암호화 | 해시 |
| --- | --- | --- |
| 방향 | 양방향 (키가 있으면 복호화) | 단방향 (원문 복원 불가) |
| 용도 | 나중에 원문이 필요할 때 | 같은지만 확인할 때 |

비밀번호는 해시한다. 로그인 시 입력값을 같은 방식으로 해시해 저장된 값과 비교한다.

## 3. 그냥 SHA-256이면 안 되나

안 된다. 두 가지 이유가 있다.

1. **너무 빠르다.** 그래픽카드 하나가 초당 수십억 번 SHA-256을 계산한다. 유출된 해시에 흔한 비밀번호 수억 개를 대입(무차별 대입)하면 금방 뚫린다. 비밀번호 해시는 일부러 **느려야** 한다.
2. **같은 입력은 같은 해시.** 공격자가 `password1`의 해시를 미리 계산해 둔 표(레인보우 테이블)로 한 번에 역조회한다. 같은 비밀번호를 쓴 회원들이 해시도 같아서 한 명이 뚫리면 동시에 드러난다.

## 4. 해법: 솔트 + 느린 해시

- **솔트(salt):** 회원마다 다른 무작위 값을 비밀번호에 섞어 해시한다. 같은 비밀번호도 해시가 달라지고, 미리 계산한 표가 무용지물이 된다.
- **작업 비용(cost):** 해시 계산을 일부러 반복해 느리게 만든다. 하드웨어가 빨라지면 cost를 올린다.

BCrypt는 이 둘을 기본 제공한다.

## 5. BCrypt 결과물 해부

```
$2a$10$N9qo8uLOickgx2ZMRZoMye IjZAgcfl7p92ldGxad68LJZdL17lhWy
│ │  │  └──── salt (22자) ────┘ └────────── 해시 (31자) ──────────┘
│ │  └ cost = 10  (2^10번 반복)
│ └ 버전
└ 구분자
```

솔트와 cost가 결과 문자열 안에 같이 들어 있다. 그래서 컬럼 하나(`passwordHash`)만 있으면 되고, 비교할 때 `matches(평문, 저장된해시)`가 알아서 솔트를 꺼내 쓴다.

```java
passwordEncoder.encode("password1");   // 호출할 때마다 결과가 다르다 (솔트가 매번 달라서)
passwordEncoder.matches("password1", 저장된해시);  // true
```

그래서 `equals`로 해시를 비교하면 안 된다. 항상 `matches`를 쓴다.

## 6. 이 프로젝트 코드에서

```java
// 가입: MemberService.signUp
.passwordHash(passwordEncoder.encode(rawPassword))

// 로그인: AuthService.login
if (!passwordEncoder.matches(request.password(), member.getPasswordHash())) { ... }
```

`PasswordEncoder`는 인터페이스이고 `SecurityConfig`가 `BCryptPasswordEncoder` 빈을 등록한다. 서비스는 구현체를 모른다. 나중에 알고리즘을 바꿔도 서비스 코드는 그대로다.

## 7. 알아둘 함정

**BCrypt는 72바이트까지만 읽는다.** 그 뒤는 무시한다(또는 예외). 한글은 글자당 3바이트라 24자만 넘어도 한계에 닿는다. 그래서 `SignUpRequest`가 비밀번호를 ASCII 출력 가능 문자(`\x21-\x7E`)로 제한해, 글자 수=바이트 수가 되게 했다. 최대 64자라 72바이트 안에 들어온다.

**로그인 실패 메시지를 통일한다.** "없는 이메일"과 "틀린 비밀번호"를 다르게 알려주면 공격자가 가입된 이메일 목록을 알아낼 수 있다(사용자 열거). `AuthService`는 두 경우 모두 `LOGIN_FAILED`를 던진다. 시간 차이로도 구분할 수 있지만(없는 이메일은 BCrypt 계산을 건너뛰어 빠름), 이 단계에서는 감수한다. 필요해지면 더미 해시 비교를 추가한다.

**비밀번호를 로그에 남기지 않는다.** 요청 로깅을 켤 때 `password` 필드를 가려야 한다. 응답 DTO에 해시도 넣지 않는다(06강).
