# 01. 인증의 기초: 인증/인가, 무상태, 세션 vs 토큰

> 이 강의 한 줄 요약: **HTTP는 기억력이 없는 직원이다. 그래서 손님이 매번 "나 누구야"를 증명할 물건(세션 쿠키 또는 토큰)을 들고 와야 한다.**

## 1. 먼저 용어: 인증과 인가

### 비유: 회사 건물 출입

회사 건물에 들어간다고 생각해 보자.

1. 1층 로비 경비원이 **사원증을 확인**한다. "당신이 김철수 맞군요." → **인증(Authentication)**
2. 엘리베이터에서 사원증을 찍었더니 **임원 층 버튼이 안 눌린다.** "김철수 씨인 건 알지만 이 층은 못 갑니다." → **인가(Authorization)**

순서가 중요하다. 누군지 모르면 권한을 따질 수조차 없다. 그래서 항상 **인증이 먼저, 인가가 나중**이다.

| 용어 | 질문 | 건물 비유 | 이 프로젝트 예 |
| --- | --- | --- | --- |
| 인증(Authentication) | 당신은 누구인가? | 로비에서 사원증 확인 | 이메일+비밀번호로 로그인 |
| 인가(Authorization) | 당신은 이걸 해도 되는가? | 층별 출입 권한 | 남의 반려동물 앨범은 볼 수 없다 (3단계) |

### 401과 403: 이름이 헷갈리는 두 상태 코드

| 코드 | 이름 | 실제 의미 | 건물 비유 |
| --- | --- | --- | --- |
| 401 | Unauthorized | **인증이 안 됨** (누군지 모름) | 사원증이 없거나 위조다. 로비에서 막힘 |
| 403 | Forbidden | 인증은 됐지만 **권한 없음** | 사원증은 진짜인데 임원 층은 못 감 |

401의 이름은 "Unauthorized(인가 안 됨)"지만 뜻은 "Unauthenticated(인증 안 됨)"에 가깝다. HTTP 명세가 오래전에 이름을 이렇게 붙여 버린 것이라 그냥 외워 두자.

- 401을 받은 클라이언트 → "다시 로그인하세요" 화면으로 보낸다.
- 403을 받은 클라이언트 → 로그인은 그대로 두고 "권한이 없습니다"를 띄운다.

이 둘을 구분해 응답해야 앱이 올바르게 반응할 수 있다. 이 구분 코드가 `SecurityConfig`에 있다(04강).

## 2. HTTP는 기억하지 못한다 (Stateless)

### 비유: 기억상실증 은행 창구 직원

은행 창구 직원이 손님이 자리를 뜨는 순간 모든 걸 잊어버린다고 해 보자.

```text
손님: (신분증 보여주며) 김철수입니다. 계좌 조회해 주세요.
직원: 네, 김철수 님 잔액은 ...입니다.
손님: 그럼 그 계좌에서 이체도 해 주세요.
직원: ...누구시죠? 처음 뵙는데요.
```

HTTP가 정확히 이렇다. 요청 하나가 끝나면 서버는 그 연결을 잊는다. 방금 로그인에 성공한 사람이 바로 다음에 보낸 요청도 서버 입장에서는 **처음 보는 요청**이다.

왜 이렇게 만들었을까? 기억하지 않으면 서버가 단순해지고, 수많은 손님을 동시에 받기 쉽다. 대신 "이 요청이 아까 로그인한 그 사람 것"이라는 증명을 **매 요청마다** 들고 와야 한다.

이 증명 수단이 두 가지 있다.

- **방법 A, 세션:** 은행이 손님에게 **번호표**를 주고, 장부에 "번호표 123 = 김철수"라고 적어 둔다.
- **방법 B, 토큰:** 은행이 손님에게 **도장 찍힌 신분 증명서**를 준다. 장부는 없다. 도장만 보면 진짜인지 안다.

## 3. 방법 A: 서버 세션 (Django 기본 방식)

### 비유: 옷 보관소 번호표

공연장 옷 보관소를 떠올리자. 코트를 맡기면 **번호표(123번)**를 준다. 번호표 자체에는 아무 정보가 없다. 그냥 숫자다. 진짜 정보(누구의 어떤 코트)는 **보관소 안쪽 선반**에 있다.

```text
1. POST /login (id, pw)
2. 서버: 맞다 → 메모리/DB/Redis에 {세션ID: 회원정보} 저장      ← 선반에 코트 걸기
3. 서버 → 클라이언트: Set-Cookie: sessionid=abc123             ← 번호표 건네기
4. 이후 요청마다 브라우저가 쿠키를 자동으로 붙임                  ← 번호표 제시
5. 서버: abc123으로 저장소를 조회해 누구인지 확인                 ← 선반에서 찾기
```

**장점**

- 번호표를 잃어버렸다고 신고하면 보관소가 선반에서 그 번호를 **지워 버리면 끝**이다. 서버가 세션을 지우면 즉시 로그아웃된다. 탈취당해도 서버가 끊을 수 있다.

**단점**

- 보관소(서버)가 **선반(상태)을 들고 있어야** 한다. 보관소를 여러 곳으로 늘리면? 1번 보관소에서 받은 번호표를 2번 보관소에 내밀면 "그런 번호 없는데요"가 된다. 그래서 서버를 늘리면 세션 저장소(Redis 등)를 공유해야 한다.
- 쿠키는 브라우저 중심 기술이라 모바일 앱과는 잘 안 맞는 면이 있다.
- **CSRF에 취약하다.** 브라우저는 쿠키를 **알아서** 붙인다. 내가 악성 사이트를 열기만 해도, 그 사이트가 몰래 우리 서버로 요청을 보내게 하면 브라우저가 내 쿠키를 자동으로 실어 보낸다. 마치 누가 내 번호표를 훔친 게 아니라, **내 손을 잡고 창구에 번호표를 내밀게 하는** 것과 같다.

## 4. 방법 B: 토큰 (이 프로젝트의 선택)

### 비유: 도장 찍힌 놀이공원 손목 밴드

놀이공원에서 입장권을 사면 **손목 밴드**를 채워 준다. 밴드에는 "자유이용권, 오늘 18시까지"라고 적혀 있고 공원의 **특수 도장(홀로그램)**이 찍혀 있다.

놀이기구 직원은 매표소에 전화해 "이 사람 표 샀나요?"라고 묻지 않는다. **밴드의 홀로그램만 보고** 진짜인지 판단한다. 매표소 장부를 뒤질 필요가 없다.

```text
1. POST /api/auth/login (email, pw)
2. 서버: 맞다 → 회원 id를 담고 서명한 토큰 발급 (서버는 저장하지 않음)   ← 밴드에 도장 찍기
3. 서버 → 앱: { "accessToken": "eyJ..." }                              ← 밴드 채워 주기
4. 앱이 토큰을 보관했다가 매 요청 헤더에 직접 붙임                         ← 손목 내밀기
      Authorization: Bearer eyJ...
5. 서버: 서명을 검증하면 저장소 조회 없이 누구인지 안다                     ← 홀로그램 확인
```

**장점**

- 서버가 **장부(상태)를 갖지 않는다.** 놀이기구 직원이 몇 명이든 같은 홀로그램 감별법(같은 비밀키)만 알면 된다. 서버를 몇 대로 늘려도 검증된다.
- Flutter 앱이 헤더에 직접 붙이기 쉽다.
- 쿠키를 쓰지 않으니 브라우저가 "알아서" 붙이는 일이 없다. 앱이 **의도적으로** 붙일 때만 전송된다. 그래서 CSRF 걱정이 없다.

**단점**

- 한번 채워 준 밴드는 **공원이 회수하기 어렵다.** 장부가 없으니 "이 밴드는 무효"라고 기록할 곳이 없다. 18시까지는 누가 차고 있든 통과된다.
- 그래서 핵심 대응은 **유효시간을 짧게** 두는 것이다(02강). 밴드가 30분짜리라면, 도둑맞아도 피해는 30분이다.

### 한눈에 비교

| | 세션 (번호표) | 토큰 (도장 찍힌 밴드) |
| --- | --- | --- |
| 정보가 어디에 있나 | 서버 저장소 | 토큰 안에 |
| 서버가 기억해야 하나 | 예 | 아니요 |
| 강제 로그아웃 | 쉬움 (지우면 끝) | 어려움 (만료까지 유효) |
| 서버 여러 대 | 저장소 공유 필요 | 같은 키만 있으면 됨 |
| 전송 방식 | 쿠키 (자동) | 헤더 (직접) |
| CSRF | 대비 필요 | 해당 없음 |

## 5. 왜 pawgeun는 토큰인가

1. **클라이언트가 Flutter 모바일 앱이다.** 앱은 브라우저처럼 쿠키를 자동 관리하지 않는다. 헤더에 토큰을 직접 붙이는 방식이 자연스럽다.
2. **서버는 화면 없이 REST API만 준다.** 세션 쿠키를 전제로 한 기능(폼 로그인 화면, CSRF 토큰)이 필요 없다.
3. **나중에 서버를 늘려도** 구조를 바꾸지 않아도 된다.

대신 지금은 **액세스 토큰만** 쓴다(유효 30분). 앱이 붙을 때 리프레시 토큰을 추가한다. 이 결정은 `docs/decisions/member-auth.md`에 이유와 함께 적었다.

## 6. Bearer란

`Authorization: Bearer {토큰}`의 Bearer는 영어로 "소지자, 가진 사람"이다. **"이 토큰을 가진 사람을 그 사람으로 취급한다"**는 뜻이다.

### 비유: 무기명 상품권

백화점 상품권에는 이름이 없다. 누가 내밀든 그 사람이 쓸 수 있다. 길에서 주운 상품권도 그대로 쓸 수 있다. Bearer 토큰이 바로 그렇다. 서버는 "이 토큰을 내민 사람이 원래 주인인가"를 따지지 않는다. **가진 사람이 곧 주인**이다.

그래서 **토큰이 새면 끝**이다. 다음 두 가지를 반드시 지킨다.

- 전송은 반드시 **HTTPS**로 한다. HTTP로 보내면 중간에서 누구나 엿볼 수 있다. 상품권을 투명 봉투에 넣어 보내는 셈이다.
- **로그에 토큰을 남기지 않는다.** 로그 파일은 생각보다 여러 사람이 본다. 로그에 찍힌 토큰은 금고 옆에 붙여 둔 비밀번호 쪽지다.

## 직접 해 보기

1. 서버를 띄우고 `curl`로 로그인한 뒤, 받은 토큰으로 `/api/members/me`를 호출해 보자. 헤더에서 `Bearer`를 빼면 어떤 응답이 오는가?
2. 같은 요청을 토큰 없이 보내면 `UNAUTHORIZED`, 엉터리 토큰을 붙이면 `INVALID_TOKEN`이 온다. 코드 어디서 이 둘이 갈리는지 `JwtAuthenticationFilter`와 `SecurityConfig.authenticationEntryPoint`에서 찾아보자.
3. 생각해 보기: 휴대폰을 잃어버렸다. 세션 방식이라면 서버가 무엇을 하면 되고, 토큰 방식이라면 무엇이 어려운가? (번호표와 손목 밴드 비유로 설명해 보자.)
