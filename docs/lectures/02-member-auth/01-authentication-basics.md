# 01. 인증의 기초: 인증/인가, 무상태, 세션 vs 토큰

## 1. 먼저 용어

| 용어 | 질문 | 이 프로젝트 예 |
| --- | --- | --- |
| 인증(Authentication) | 당신은 누구인가? | 이메일+비밀번호로 로그인 |
| 인가(Authorization) | 당신은 이걸 해도 되는가? | 남의 반려동물 앨범은 볼 수 없다 (3단계) |

401 Unauthorized는 이름과 달리 "인증이 안 됨"이다. 403 Forbidden은 "누군지는 알지만 권한이 없음"이다. 이 둘을 구분해 응답하는 코드가 `SecurityConfig`에 있다.

## 2. HTTP는 기억하지 못한다 (Stateless)

HTTP 요청 두 개는 서로를 모른다. 서버 입장에서 방금 로그인한 사람의 다음 요청은 "처음 보는 요청"이다. 그래서 "이 요청이 아까 로그인한 그 사람 것"임을 증명할 방법이 매 요청에 필요하다. 이 증명 수단이 세션 또는 토큰이다.

## 3. 방법 A: 서버 세션 (Django 기본 방식)

```
1. POST /login (id, pw)
2. 서버: 맞다 → 메모리/DB/Redis에 {세션ID: 회원정보} 저장
3. 서버 → 클라이언트: Set-Cookie: sessionid=abc123
4. 이후 요청마다 브라우저가 쿠키를 자동으로 붙임
5. 서버: abc123으로 저장소를 조회해 누구인지 확인
```

- 장점: 서버가 세션을 지우면 즉시 로그아웃시킬 수 있다. 탈취당해도 서버에서 끊을 수 있다.
- 단점: 서버가 상태를 들고 있다. 서버를 여러 대로 늘리면 세션 저장소를 공유해야 한다. 쿠키는 브라우저 중심이라 모바일 앱과는 맞지 않는 면이 있다.
- 쿠키는 브라우저가 자동으로 붙이므로 **CSRF**(다른 사이트가 내 쿠키를 이용해 요청을 보내게 하는 공격)에 취약하다.

## 4. 방법 B: 토큰 (이 프로젝트의 선택)

```
1. POST /api/auth/login (email, pw)
2. 서버: 맞다 → 회원 id를 담고 서명한 토큰 발급 (서버는 저장하지 않음)
3. 서버 → 앱: { "accessToken": "eyJ..." }
4. 앱이 토큰을 보관했다가 매 요청 헤더에 직접 붙임
      Authorization: Bearer eyJ...
5. 서버: 서명을 검증하면 저장소 조회 없이 누구인지 안다
```

- 장점: 서버가 상태를 안 갖는다. 서버가 몇 대든 같은 비밀키만 있으면 검증된다. Flutter 앱이 헤더로 직접 붙이기 쉽다. 쿠키를 안 쓰니 CSRF 걱정이 없다.
- 단점: 발급한 토큰을 서버가 마음대로 무효화하기 어렵다. 그래서 유효시간을 짧게 두는 것이 핵심 대응이다 (02강).

## 5. 왜 pawfect는 토큰인가

1. 클라이언트가 Flutter 모바일 앱이다. 헤더에 토큰을 붙이는 방식이 자연스럽다.
2. 서버는 화면 없이 REST API만 준다. 세션 쿠키 전제의 기능(폼 로그인, CSRF 토큰)이 필요 없다.
3. 나중에 서버를 늘려도 구조를 바꾸지 않아도 된다.

대신 지금은 **액세스 토큰만** 쓴다(유효 30분). 앱이 붙을 때 리프레시 토큰을 추가한다. 이 결정은 `docs/decisions/member-auth.md`에 이유와 함께 적었다.

## 6. Bearer란

`Authorization: Bearer {토큰}`의 Bearer는 "이 토큰을 가진 사람(소지자)을 그 사람으로 취급한다"는 뜻이다. 열쇠와 같다. 가진 사람이 곧 주인이므로 **토큰이 새면 끝**이다. 그래서 전송은 반드시 HTTPS로, 로그에는 토큰을 남기지 않는다.
