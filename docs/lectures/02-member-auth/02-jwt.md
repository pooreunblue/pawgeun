# 02. JWT 깊게 보기

> 이 강의 한 줄 요약: **JWT는 "누구나 읽을 수 있는 엽서"에 "위조할 수 없는 밀랍 도장"을 찍은 것이다. 내용은 숨기지 못하지만, 바꾸면 들킨다.**

JWT(JSON Web Token)는 "누구인지"를 담은 JSON을 **서명해서** 문자열로 만든 것이다. 서버는 이 문자열을 DB에서 찾지 않고 서명만 검증해 신뢰한다.

## 1. 구조: 점 두 개로 나뉜 세 덩어리

### 비유: 봉투 없는 엽서 + 밀랍 도장

옛날 왕이 보내는 편지를 떠올리자.

- **Header** = 엽서 맨 위의 "이 도장은 왕실 문장 방식으로 찍었음" 메모
- **Payload** = 엽서 본문. "이 사람은 42번 회원이다. 18시까지 유효."
- **Signature** = 왕실만 가진 인장으로 찍은 **밀랍 도장**

엽서라서 **배달부도, 옆 사람도 본문을 읽을 수 있다.** 하지만 본문을 고쳐 쓰면 도장 모양이 맞지 않게 되어 위조가 들통난다.

```text
eyJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJwYXdnZXVuIiwic3ViIjoiNDIifQ.(서명 값)
└─ Header ─┘ └─── Payload ───┘ └─ Signature ─┘
```

각 덩어리는 Base64URL로 인코딩한 것이다. **암호화가 아니다.** Base64는 "글자를 전송하기 좋은 모양으로 바꾼 것"일 뿐, 자물쇠가 아니다. 한글을 초성으로만 적은 것처럼, 규칙만 알면 누구나 원래대로 되돌린다.

```bash
# 직접 풀어 보자
# 끝의 = 는 패딩이다. JWT에서는 생략되어 있어 직접 붙여야 한다
# Base64는 4글자 단위다. 이 덩어리는 38글자라 4의 배수(40)까지 = 를 2개 붙인다
# (1개만 붙이면 마지막 } 가 잘려서 나온다)
echo 'eyJpc3MiOiJwYXdnZXVuIiwic3ViIjoiNDIifQ==' | base64 -d
# 출력: {"iss":"pawgeun","sub":"42"}
```

| 덩어리 | 내용 | 예 | 엽서 비유 |
| --- | --- | --- | --- |
| Header | 서명 알고리즘 | `{"alg":"HS256"}` | 도장 방식 메모 |
| Payload | 클레임(주장) 모음 | `{"iss":"pawgeun","sub":"42","iat":...,"exp":...}` | 본문 |
| Signature | 앞 두 덩어리를 비밀키로 서명한 값 | `HMAC-SHA256(header.payload, 비밀키)` | 밀랍 도장 |

**결론 1: payload에 비밀번호나 개인정보를 넣지 않는다.** 엽서 본문에 카드 비밀번호를 쓰지 않는 것과 같다. pawgeun는 회원 id만 넣는다.

## 2. 서명이 하는 일

### 비유: 내용물로 만들어지는 도장

JWT의 도장은 특이하다. 미리 새겨 둔 도장이 아니라, **본문 내용 + 비밀키**를 섞어서 그때그때 도장 모양을 만든다. 본문이 한 글자만 달라도 도장 모양이 완전히 달라진다.

서명은 두 가지를 증명한다.

1. **무결성:** 내용이 중간에 안 바뀌었다.
2. **출처:** 비밀키를 가진 서버(우리)가 만들었다.

```text
공격자가 payload의 sub를 42 → 1 로 바꿈 (남의 계정을 노림)
   → 서명은 원래 payload("42")로 계산된 값이라 더 이상 맞지 않음
   → 서버가 받은 payload("1")로 같은 계산을 해 보면 서명이 불일치 → 거부
```

공격자가 바뀐 내용에 맞는 서명을 새로 만들려면 비밀키가 있어야 한다. 비밀키는 서버만 안다.

**결론 2: 비밀키가 곧 서버의 신뢰다.** 왕실 인장을 도둑맞으면 누구나 왕의 편지를 위조할 수 있다. 비밀키가 유출되면 누구나 아무 회원의 토큰을 만들 수 있다.

이 동작은 `JwtProviderTest.내용을_바꾼_토큰은_거부한다`가 그대로 재현한다.

## 3. 클레임

클레임(claim)은 영어로 "주장"이다. 토큰이 "나는 42번 회원이다", "나는 18시까지 유효하다"라고 **주장**하는 항목들이다. 서명이 맞으면 서버는 이 주장을 믿는다.

자주 쓰는 것은 표준 이름이 정해져 있다(등록 클레임). 3글자로 짧게 지은 것은 토큰 크기를 줄이기 위해서다.

| 이름 | 원래 단어 | 뜻 | pawgeun에서 | 신분증 비유 |
| --- | --- | --- | --- | --- |
| `iss` | issuer | 발급자 | `"pawgeun"`. 파싱 때 `requireIssuer`로 확인 | 발급 기관 (OO구청장) |
| `sub` | subject | 주체. 누구의 토큰인가 | 회원 id 문자열 | 이름/주민번호 |
| `iat` | issued at | 발급 시각 | 발급 순간 | 발급일 |
| `exp` | expiration | 만료 시각 | 발급 + 30분 | 유효기간 |

`iss`를 확인하는 이유: 검사는 두 단계로 나뉜다.

1. **서명 검증**(`verifyWith(key)`): "우리 키로 찍은 도장이 맞는가"를 본다. 키가 다른 곳에서 만든 토큰은 여기서 이미 탈락한다.
2. **`iss` 검사**(`requireIssuer`): 서명이 통과한 토큰에 대해 "발급자 칸에 `pawgeun`이라고 적혀 있는가"를 한 번 더 본다. 실수로 다른 용도의 토큰이 섞여 들어오는 것을 막는 이중 확인이다.

한계도 알아 두자. `iss`는 **발급하는 쪽이 적어 넣는 글자**일 뿐이다. 만약 같은 키를 다른 서비스와 공유한다면, 그 서비스도 `iss`에 `"pawgeun"`이라고 적어 정상 서명을 할 수 있다. 즉 **`iss`만으로는 키를 공유한 발급자들을 구별할 수 없다.** 발급자 구별의 진짜 근거는 키이므로, 키는 서비스마다 따로 두고 공유하지 않는다.

비유: 도장(서명)이 진짜인지 먼저 보고, 그다음 "발급 기관" 칸을 읽는다. 하지만 같은 도장을 두 구청이 나눠 쓴다면 "발급 기관" 칸은 아무나 적을 수 있으니 믿을 근거가 못 된다.

파싱 라이브러리는 `exp`가 지났으면 알아서 예외를 던진다(`ExpiredJwtException`). 직접 시간 비교 코드를 쓰지 않는다. 직접 쓰면 시간대, 경계값(같은 초) 같은 실수를 하기 쉽다.

## 4. 알고리즘: HS256 vs RS256

### 비유: 같은 열쇠 vs 자물쇠와 열쇠

- **HS256 (대칭키):** 도장을 찍는 사람과 도장을 확인하는 사람이 **같은 인장**을 갖는다. 확인할 수 있는 사람은 곧 찍을 수도 있다.
- **RS256 (비대칭키):** 찍는 인장(개인키)은 본사만 갖고, 지점들은 **"진짜 도장 모양 견본"(공개키)**만 받는다. 견본으로는 확인만 되고 찍을 수는 없다.

| | HS256 (HMAC) | RS256 (RSA) |
| --- | --- | --- |
| 키 | 비밀키 하나로 서명·검증 | 개인키로 서명, 공개키로 검증 |
| 적합 | 서버가 발급과 검증을 둘 다 함 | 발급 서버와 검증 서버가 다름 |
| 단점 | 검증하는 쪽도 비밀키를 알아야 함 | 키 관리가 더 복잡 |

pawgeun는 서버 하나가 발급·검증을 다 한다. 본사가 혼자 찍고 혼자 확인하니 견본을 나눠 줄 일이 없다. HS256이면 충분하다.

HS256 키는 **256비트(32바이트) 이상**이어야 한다. 짧은 키는 짧은 비밀번호처럼 무차별 대입으로 뚫린다. `JwtProvider` 생성자의 `Keys.hmacShaKeyFor`가 짧으면 예외를 던지고, 그러면 서버가 기동 단계에서 죽는다. 약한 키로 조용히 운영되는 것보다 낫다. 고장 난 자물쇠로 문을 잠근 척하는 것보다, 아예 "자물쇠 불량"이라고 문을 열지 않는 편이 안전하다(`JwtProviderTest.키가_256비트보다_짧으면_기동_단계에서_실패한다`).

## 5. 코드 읽기

### 발급 (도장 찍기)

```java
Jwts.builder()
    .issuer("pawgeun")                                  // 발급자: 우리 서비스
    .subject(String.valueOf(memberId))                  // 주체: 회원 id (문자열로)
    .issuedAt(now)                                      // 발급 시각
    .expiration(new Date(now.getTime() + 유효시간))       // 만료 시각 = 지금 + 30분
    .signWith(key, Jwts.SIG.HS256)                      // 서명 알고리즘을 HS256으로 명시
    .compact();                                         // header.payload.signature 문자열로 직렬화
```

### 검증 (도장 확인)

```java
Jwts.parser()
    .verifyWith(key)            // 서명 검증용 키
    .requireIssuer("pawgeun")   // iss가 다르면 거부
    .build()
    .parseSignedClaims(token)   // 서명·만료·형식을 한꺼번에 검증
    .getPayload();              // 통과하면 클레임(본문)을 꺼냄
```

`parseSignedClaims`는 **서명된** JWT만 받는다. Header에 `alg: none`(서명 없음)이라고 적힌 토큰을 받으면 거부한다는 뜻이 메서드 이름에 들어 있다.

이게 왜 중요할까? 과거에 일부 라이브러리가 "도장 방식: 없음"이라고 적힌 엽서를 받으면 **도장 확인을 건너뛰고 통과**시키는 취약점이 있었다. 공격자는 본문을 마음대로 쓰고 `alg: none`만 붙이면 됐다. 경비원이 "이 출입증은 확인 안 해도 됨"이라고 적힌 쪽지를 믿어 버린 셈이다.

## 6. 위험과 대응

| 위험 | 설명 | 비유 | pawgeun의 대응 |
| --- | --- | --- | --- |
| 토큰 탈취 | 가진 사람이 곧 주인 | 손목 밴드를 뺏김 | HTTPS 전제, 유효시간 30분으로 짧게 |
| 비밀키 유출 | 임의 토큰 위조 가능 | 왕실 인장 도난 | 기본값 없이 환경변수 `JWT_SECRET`만 사용(없으면 서버가 안 뜸), 저장소에 키 커밋 금지 |
| 서버가 토큰을 못 끊음 | 탈퇴·정지한 회원의 토큰이 만료 전까지 유효 | 퇴사자 출입증이 유효기간까지 살아 있음 | 요청마다 회원 존재를 조회(`getById`)하므로 탈퇴 회원은 `MEMBER_NOT_FOUND`. 완전한 폐기는 리프레시 토큰 도입 때 |
| payload 노출 | 누구나 읽음 | 엽서 본문 | 민감정보를 넣지 않음 |

세 번째 행이 재미있다. 토큰 서명은 여전히 진짜지만 그 사람은 이미 탈퇴했다. 출입증은 진짜인데 사원 명부에는 이름이 없는 상황이다. pawgeun는 `/me` 같은 요청에서 명부(DB)를 한 번 더 확인하므로 걸러진다.

## 7. 액세스 토큰과 리프레시 토큰 (다음에 추가할 것)

토큰이 짧으면 안전하지만 30분마다 재로그인하는 건 번거롭다. 그래서 두 개를 쓴다.

### 비유: 일일 출입증과 사원증

- **액세스 토큰 = 일일 방문증.** 어느 문이든 찍고 다닌다. 유효시간이 짧아서 잃어버려도 금방 무효가 된다.
- **리프레시 토큰 = 사원증.** 문을 여는 데는 안 쓴다. 오직 **안내 데스크에서 새 방문증을 받을 때만** 내민다. 안내 데스크는 사원증 목록(DB)을 갖고 있어서, 분실 신고된 사원증은 거절할 수 있다.

```text
액세스 토큰: 짧음(30분). 모든 API 호출에 사용. 탈취돼도 피해 시간이 짧다.
리프레시 토큰: 김(2주). 액세스 토큰 재발급 전용 주소에서만 사용. 서버 DB에 저장해 폐기 가능.
```

로그아웃·분실 시 서버가 리프레시 토큰을 지우면 재발급이 막힌다. 이미 발급된 액세스 토큰은 만료(30분)까지 쓸 수 있으므로, 접근은 길어도 30분 안에 끊긴다. 즉시 차단하려면 별도의 블랙리스트(무효 토큰 목록)가 필요하다. 앱을 붙일 때 추가한다.
